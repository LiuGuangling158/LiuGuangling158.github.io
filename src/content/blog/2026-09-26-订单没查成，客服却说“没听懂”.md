# 订单没查成，客服却说“没听懂”

> **系列**：MewHelp Agent 踩坑日志
> **关键词**：意图识别、异常兜底、结构化输出、tool_calls

## 一、这次部署真的遇到了这个问题

本机服务启动后，首页能打开，知识库的 52 条向量也写进去了。按部署文档发出第一条验收问题：

```text
订单 1001 的物流到哪了
```

结果没有调用任何工具，只回了一句：

```text
抱歉，我不太确定您的意思。您可以把问题说得更具体些吗？
```

这句话很容易让人先怀疑意图识别的提示词。可问题已经足够明确，再加几句“请准确识别物流意图”也没用。

检查应用日志，才看到两次 `AuthenticationError`。聊天接口返回了 `401`，错误内容是 `Api key is invalid`。

当时 `.env` 中的聊天密钥和嵌入密钥不同。嵌入接口成功了，只能说明建库那条链路可用，聊天请求根本没通过鉴权。换成项目里已经验证有效的同一硅基流动密钥，重启后再问，`query_order` 和 `query_logistics` 就正常执行了。

## 二、为什么鉴权失败会变成“没听懂”

原因在意图识别的异常处理里。相关代码的意思是：

```python
# 精简示意
try:
    result = await intent_chain.ainvoke(payload)
except Exception:
    return {"intent": "其他", "confidence": 0.0}
```

鉴权失败、超时、结构化解析失败，都会进入这里。随后路由把“其他”交给固定话术，于是用户看到的是“没听懂”。

```text
聊天接口 401
    ↓
意图识别捕获异常
    ↓
返回“其他”，置信度 0
    ↓
固定话术：“请说得更具体一些”
```

程序没有崩，但页面把真实故障藏起来了。这次排查能定位，靠的是底层日志保留了异常类型。当前实现仍然使用这个兜底，后续值得把“问题不明确”和“上游调用失败”分开处理。

## 三、密钥没问题，也不一定拿得到结构化结果

鉴权只是这次部署的原因。代码里还记录了另一类问题：接口返回了响应，但没有拿到可用的结构化对象。

例如，部分通道会把工具参数拼成这样：

```text
{}{"useful": true}
```

还有一种更隐蔽：响应中没有预期的 `tool_calls`，解析器直接返回 `None`。如果只捕获异常，程序会继续往下走，直到访问 `result.intent` 才出错。

项目在 `llm.structured()` 里显式使用 Function Calling：

```python
fc = m.with_structured_output(schema, method="function_calling")
```

拿到结果后还要检查是不是 `None`。异常或空结果会原样重试一次，两次都失败就抛给调用点，不再当作成功结果继续传递。

## 四、别把一种通道的修法套到所有模型上

这个封装默认开流式，但对名字匹配 MiniMax 家族的模型关闭流式。仓库记录的原因是：不同通道返回工具调用的行为并不一致，有的非流式参数会坏，有的流式拿不到工具调用。

所以换模型后，除了发一句“你好”，还得跑一次真的需要结构化结果的请求。检查的内容也要具体：有没有工具调用、参数能不能解析、返回对象是不是空、失败日志能不能定位到上游。

意图识别、证据自检和滚动摘要已经用了这个封装。知识挖掘和第 10 章预标仍有直接调用 `with_structured_output()` 的地方，不能因为有了公共封装，就默认其他入口也都处理好了。

## 核心要点

看到“没听懂”时，先查这一轮的调用日志。密钥、网络和解析失败，都可能被包装成同一句客服话术。确认模型实际收到了问题，再去调整提示词。
